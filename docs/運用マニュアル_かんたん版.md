**ラクシフトAI** を日常運用するために必要な操作を、**手順通りにやれば誰でもできる** ように書いています。

詳しい技術仕様は [`引き継ぎ資料_完全版.md`](引き継ぎ資料_完全版.md) を、セキュリティは [`SECURITY.md`](SECURITY.md) を参照してください。

## 🏗️ システム全体像

```
お客さん（ブラウザ）
    ↓ アクセス
[Cloudflare Pages] ← HTMLとJavaScriptを配信するサーバー
    ↓ データ取得
[Supabase] ← データベース (PostgreSQL + RLS、29本のmigration)
    ↓ シフト生成
[Railway] ← AIがシフトを計算するサーバー (Python FastAPI)
    ↓ 決済
[Stripe] ← クレジットカード決済 + Webhook
    ↓ AI 監査
[Google Gemini] ← LLM によるシフト品質チェック
```

## 📋 日常業務

### 1. 新しい顧客が契約したとき

**自動でこうなります:**
```
お客さんが Stripe で決済
  ↓ 自動 (webhook)
テナント (契約ID) が自動作成
  ↓ 自動
顧客メールに案内メール送信 (SMTP リトライ 3回付き)
```

**あなたがやること:**
1. `admin.html` にログイン
2. 「テナント管理」タブで新規テナント確認
3. メールが届いていなければ「案内送信」ボタンで再送

### 2. お客さんから「複数店舗を統括したい」と言われたとき (新機能 v32)

**手順:**
1. `admin.html` →「本部管理」タブ
2. 「本部アカウント発行」モーダル
3. ログインID (例: `hq_chain_a`)、パスワード (自動生成可)、会社名、管轄店舗を選択
4. 発行 → ID/パスワードを控えて顧客にメール通知
5. 顧客は `index.html` の「本部ログイン」で接続

詳細は [本部管理者マニュアル.md](本部管理者マニュアル.md) を参照。

### 3. お客さんからパスワードを忘れたと言われたとき

**A案 (運営者判断項目を維持中の場合):**
- マスターパスワード `rakushift1234` でログインしてもらう
- ログイン後、設定画面で新しいパスワードに変更してもらう

**B案 (マスターパスワード削除後):**
- 運営者が `admin.html` から該当テナントのパスワードリセット (将来機能)

### 4. お客さんのプラン変更
お客さん自身で変更可能:
1. ログイン → 「プラン管理」
2. 「プラン変更」→ Stripe ポータル → 新プラン選択
3. 自動反映 (webhook)

### 5. 決済失敗時
**自動でこうなります:**
```
決済失敗 → 画面オレンジ警告
  ↓ 21日間放置
自動ライセンス停止
  ↓ 6ヶ月後
削除予定リストに表示 (admin.html テナント管理タブ)
  ↓ 運営者が手動「物理削除」ボタン
完全削除
```

### 6. 法人お問い合わせ対応 (新機能)
`admin.html` →「お問い合わせ」タブ:
- 新規件数バッジで未対応を一目把握
- 詳細モーダルでステータス変更 (new → contacted → in_progress → closed/spam)
- 担当者割り当て + 内部メモ記入

## 🚀 デプロイ (更新の反映)

### コード変更
```bash
# フロントを変更した場合: お客様端末のキャッシュ破棄
pwsh scripts/bump-version.ps1

git add -A
git commit -m "修正内容"
git push origin main
```
→ Cloudflare Pages が約1-2分でフロント反映、Railway が約3-5分でバックエンド反映

### 📢 お客様にスーパーリロードを依頼する必要はあるか?

**いいえ、不要です** (キャッシュ戦略が組み込み済み):

| 状況 | 必要操作 | 理由 |
|---|---|---|
| デプロイ後、ユーザーが次回サイトを開く | **何もしなくて OK** | HTML は `Cache-Control: no-cache` で毎回最新。新しい `?v=` で JS も新版取得 |
| ユーザーが既にタブを開きっぱなし | 通常のリロード (F5) | HTML の no-cache が効くため新版を取得 |
| 緊急で全顧客に新版反映したい | `bump-version.ps1` 実行 → git push | 全 JS の `?v=` が新値になる |

ただし **デプロイ時は必ず `pwsh scripts/bump-version.ps1` を実行** してから git push してください。これを忘れると、JS が古いまま残ります。

仕組み詳細は [DEPLOYMENT.md §3.1](DEPLOYMENT.md) と [`_headers`](../_headers) ファイルを参照。

### DB マイグレーション
新しい `supabase/migrations/*.sql` を `git push` すると `.github/workflows/supabase_migrate.yml` が自動実行 (Slack 失敗通知付き)。

## ⚠️ 店舗オーナーへの案内ポイント (重要)

設定の正確さがAIの精度を100%決めます。

### 🟢 正確に設定した場合
- 店舗情報: 営業時間、時間帯別の必要人数、店舗独自のポジション (ホール/キッチン等)、管理者の必須カバー
- スタッフ: NGペア・必須ペア、週の最低出勤日数、希望時間考慮、役職、担当ポジション
- → 店長顔負けの完璧なシフトを全自動生成

### 🔴 設定が甘い場合
- 必要人数すべて0、希望休だけ入力 → AI は「制限なし」と判断 → 連勤・人員不足のシフトが出る

## 🤖 AIシフト生成の仕組み

```
① お客さんが「AIシフト作成」ボタン
② 人員チェック (/check)
③ MILP ソルバ (PuLP) で計算 (/generate)
④ Gemini AI で監査 (品質保証)
⑤ プレビュー画面で確認
⑥ 確定保存 or キャンセル
```

**赤斜線の太枠 = イレギュラーシフト** (人手不足時の妥協配置、必ず店長が目視確認)

## 🛠️ トラブルシューティング

### シフト生成ができない
| チェック | 確認方法 |
|---|---|
| Railway 起動中 | https://rakushift-ai-production.up.railway.app/health に GET → `{"status":"ok"}` |
| Supabase 起動中 | Supabase Dashboard でプロジェクトがアクティブか |
| スタッフ数プラン超過 | 赤い警告バナー有無 |

### ログインできない
| チェック | 確認方法 |
|---|---|
| 契約ID | 管理画面のテナント一覧で確認 |
| パスワード | マスター `rakushift1234` を試す |
| ロックアウト | 10回失敗で5分ロック、`login_attempts` テーブル確認 |

### 本部アカウントが店舗を見られない
| 症状 | 対処 |
|---|---|
| 0店舗表示 | スコープ未設定 → admin.html 「本部管理」タブでスコープ追加 |
| 「貴社の管轄外」 | スコープ追加またはグローバル本部へ昇格を検討 |
| 「セッションが古いため再ログイン」 | 自動ログアウト → 再ログイン (新スキーマ反映) |

## ⚠️ やってはいけないこと

1. **`js/config.js` をフォーク先で公開しない** (Supabase Anon Key 公開前提だが、自社向けに分離する場合)
2. **`platform_settings` テーブルを直接編集しない** (Stripeキー等が壊れる)
3. **テナントを手動で DB から直接削除しない** (関連データ残る → `delete_tenant_data` RPC 使用)
4. **Railway `SUPABASE_SERVICE_KEY` を外部に漏らさない**
5. **Supabase Personal Access Token (PAT) を Git にコミットしない** (`.gitignore` で除外済み)
6. **マスターパスワード `rakushift1234` をマーケ資料に書かない** (将来削除予定)

## 📞 緊急時の対応

| 状況 | 対応 |
|------|------|
| サイトが完全に落ちた | Cloudflare → Railway → Supabase の順に確認、`/health` チェック |
| 決済が止まった | Stripe Dashboard でイベントログ確認、webhook 署名検証エラー有無 |
| データが消えた | Supabase の自動バックアップから復元 (Pro 以上) |
| 不正アクセスの疑い | Railway logs 確認、`auth_sessions` 全削除、PAT/Service Key ローテーション |
| 顧客本部が他社のデータを見ている | 即座に該当本部のスコープを確認 (`admin.html` 本部管理タブ)、必要なら本部削除 |
